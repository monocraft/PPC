# SharePoint publication and encrypted package delivery

## Decision and present evidence

The owner selected **Automatic opening with encrypted backend copy**, after being told this adds storage/download usage. SharePoint is the publication of record; the existing Supabase project retains one byte-identical encrypted current package and at most one additional candidate/cleanup object. GitHub remains the code/site host and trusted package producer. Existing HP ChatGPT Outlook/SharePoint connections remain the only Microsoft credentials. No new Microsoft application, service identity or package key is introduced.

Baseline: `1d120378a4e2c634dc363ec8eaafda5d1f184de4`. Hosted execution and a genuine sandbox file/raw SharePoint download are verified. The currently published encrypted package was separately copied to the existing SharePoint `master_ppc.pkg`, version 4.0, with matching raw readback: 45,439,227 bytes, SHA-256 `d1af8e0e7fd1782a2b52433a38b62db227cc42a999179fb3ddd7d7d2bee1b7e2`; version 3.0 remains. The pinned digest must match `/^[a-f0-9]{64}$/` before any seed request. Private seed evidence remains in the ignored operations record. This does not establish ongoing publication, browser delivery, custom MCP authentication or scheduled report processing.

## Fixed scope and trust boundaries

- Backend bytes stay encrypted; never decrypt, persist plaintext, or provision another package key. Preserve full image archives, owner metadata/retirement receipts, MSRP, conflicts, accepted facts and local drafts.
- GHA producer authenticates control calls with existing `X-PPC-Publisher-Secret`; its existing `PPC_PACKAGE_KEY` stays inside Actions. Supabase service credentials stay inside Edge Functions. Publisher credentials never enter MCP/browser/download requests.
- Cloud publication tools reuse the exact existing managed owner/client/resource OAuth verifier. They may retrieve the sole queued candidate and acknowledge its exact SharePoint readback, never reserve arbitrary packages or export a plaintext master.
- Browser `POST /api/package/latest` accepts only `{key}` over TLS, normalizes/hashes it using existing `PPC_PACKAGE_KEY_HASH`, and streams current ciphertext. It receives no Microsoft or publisher credentials. Do not log/store its key. Reuse exact allowed-origin CORS and rate limiting; authentication precedes Storage reads.
- Fixed private bucket: `ppc-package-delivery`, maximum object size **67,108,864 bytes**, MIME `application/octet-stream`, no public/anon/authenticated object policies. Existing service-role adapter alone signs/reads/deletes. Browser and OAuth JWTs cannot access Storage directly.
- Provider must be `sharepoint`; host must be `hp.sharepoint.com`; approved folder is `/teams/PCGamingCategory/Shared Documents/Product Portfolio/PPC`. Server-only `PPC_PACKAGE_SP_DRIVE_ID` and `PPC_PACKAGE_SP_FOLDER_ID` must match the already verified seeded folder at activation. Caller-supplied hosts, folders, paths and signed-upload destinations are forbidden.
- No new inbox/package/browser health polling, Microsoft keepalive, desktop runtime, broad fetch proxy, package base64/JSON transport or token extraction. Existing publisher dispatch remains event based; any existing scheduled publisher behavior is unchanged until the reviewed cutover.

## Persisted contract and state machine

Migration `202610170005_package_delivery.sql` adds private singleton delivery policy/state and immutable publication receipts, accessible only through restricted service-role RPCs. Policy phases are `legacy` (default), `seeding`, `sharepoint`; all new runtime paths also require `PPC_PACKAGE_DELIVERY_ENABLED=true` (default false). Source preparation cannot switch phases.

`Candidate = {candidateId: UUID, kind:'seed'|'publication', generation: positive integer, expectedGeneration: integer, storageRevision: integer, sourceSha: 40hex, manifestSha256: 64hex|null, ownerImagesCommit: 40hex|null, sha256: 64hex, bytes: integer, objectKey, createdAt, expiresAt, status}`. The route derives kind; callers cannot relabel seed as publication. `manifestSha256` is required 64-hex for publication and null only for the separately pinned historical seed. `sourceSha` is the original trusted seed's 40-hex identity retained by the existing master export, not the latest package blob/ciphertext digest. `ownerImagesCommit` binds the optional requested immutable owner-image input commit; ordinary publication/seed uses null. Bytes must be 36..67,108,864 and begin with the supported encrypted envelope. `generation = expectedGeneration + 1`; object key is exactly `packages/<candidateId>.pkg`. Status transitions are `reserved -> ready -> published`, or `reserved/ready -> cleanup`. A published object becomes the current pointer without copying; the preceding current becomes the one cleanup slot. Never overwrite/upsert object contents.

`Receipt = {provider:'sharepoint', kind:'seed'|'publication', candidateId, generation, storageRevision, sha256, bytes, driveId, folderId, itemId, versionId, fileName, confirmedAt}`. Normal filename is exactly `master-r<storageRevision>-g<generation>-<candidateId>.pkg`. Item/version IDs must be real connector results, bounded nonempty text; they are not hashes. The seed alone permits the previously verified `master_ppc.pkg` version 4.0. Retain receipts after deleting superseded ciphertext.

Ordinary reservation binds exported source/revision/manifest digest, `ownerImagesCommit` and the prior publication generation under a row lock. Private export adds `acceptedManifestSha256`, computed in PostgreSQL as `encode(sha256(convert_to(manifest::text,'UTF8')),'hex')` over the accepted JSONB manifest, before owner-image projection. The producer copies this backend value into candidate `manifestSha256`; it does not recreate PostgreSQL JSON serialization in JavaScript. SQL reserve compares it to the current locked row's digest in the same transaction. Verify native PostgreSQL/PGlite `sha256(bytea)` locally; unsupported behavior blocks implementation rather than silently changing canonicalization. Existing projected package `marker.manifestDigest` retains its current JavaScript canonical digest and separate meaning. Reject future/stale revisions, inconsistent retries and a second candidate. Same-revision owner-image updates are permitted with a new generation/ciphertext digest; queued image B never satisfies requested A. Exact retry identity includes source/revision/accepted-manifest digest/ownerImagesCommit/ciphertext digest/bytes/expectedGeneration. Seed instead validates trusted already-published bytes and uses null manifestSha256. `finalize` verifies actual stored envelope/size/SHA-256 before ready; ETag alone is insufficient. Storage identity is immutable after finalization.

Reservation expires after **3 hours**; it grants no externally usable write capability. The producer uploads ciphertext through a publisher-secret authenticated **binary PUT** in a separate `ppc-package` Edge Function, outside the existing JSON gateway's size limit. The handler claims candidate ownership before reading its body, rejects stale/closed/generation-mismatched candidates, and streams to the exact private Storage key with create-only semantics and a **120-second** transfer deadline. Hash/length/envelope verification runs incrementally on the forwarded stream; never issue a signed Storage WRITE URL. Supabase signed-upload URLs remain usable for two hours and would otherwise allow deleted orphan recreation. Signed READ capabilities last at most **5 minutes** and cannot create objects.

Acknowledgement revalidates ready/unexpired candidate, pinned destination/name, expectedGeneration and actual readback hash/bytes; CAS atomically records receipt, advances current pointer/generation and existing published revision. A later accepted database revision may stay pending. An exact repeated acknowledgement returns its immutable receipt even after candidate expiry or a newer current generation; conflicting/stale claims fail. For that historical internal service retry only, SQL may recover absent `kind` and `storageRevision` from the already immutable exact receipt. It must match every other identity/provenance field and return only `already_published`; new or never-published candidates receive no such recovery. SQL owns confirmation time. Image-only changes advance generation without inventing a business revision. Old GitHub `ack` cannot advance qualifying publication in `sharepoint` phase.

Cleanup is driven only by reserve/finalize/ack/user delivery activity: delete at most one recorded cleanup object per operation, then clear its slot after confirmed absence AND no unsettled upload owner. No next reservation exists until that slot is cleared. Persist an upload attempt ID/state before opening Storage; a crashed/uncertain upload is recovered by reading/verifying its exact object, or holds the slot for explicit operator reconciliation when completion/absence cannot be proven. Reservation/lease expiry alone must not delete/release a possibly in-flight write. Failed deletes also hold the slot. Paths derive only from persisted UUIDs; no bucket listing/arbitrary deletion. Superseded current bytes may be deleted once ownership settles; a stale signed reader can retry the new current rather than forcing more retained copies. An idle leftover is bounded to one object and cleaned at the next real operation; receipts/policy remain. Maximum ciphertext is current + one candidate/cleanup object = **128 MiB**, including failed/uncertain operations.

## Source interfaces and flow

Canonical contract module: `supabase/functions/ppc-master/package-delivery-contract.mjs` exports limits, strict metadata validation and `qualifiesSharePointPublication(publication, receiptRevision)`. Public snapshots add sanitized `{provider,kind,generation,candidateId,sha256,bytes,storageRevision,publishedAt}`; no Storage paths/capabilities or private destination identifiers. The Archive qualifier requires `kind:'publication'`; a seed receipt alone always fails. Retain legacy `githubSha` for legacy mode only; SHA-256 is authoritative in SharePoint mode.

Separate function `supabase/functions/ppc-package/index.ts` serves `/api/package/{current,reserve,finalize,seed,latest}` and `PUT /api/package/candidates/<UUID>/bytes`. Factory `createPackageDelivery({env,database,storage,now})` in its `core.mjs` produces `publisher(operation,payload)`, `upload(request,candidateId)`, `getQueuedPublication()`, `confirmPublication(input)`, `reader(request)` and `publicState()`; `http.mjs` owns strict route/method/CORS/auth/body dispatch. Control operations use <=32 KiB JSON and the existing publisher secret; binary PUT uses `application/octet-stream`, `Content-Length` and `X-PPC-Candidate-Generation` equal to the reservation. `current` returns `{current,queued}` plus five-minute current download capability, not plaintext; queued state permits lost-reply/restart recovery. `latest` preserves the existing reader `{key}` -> binary contract. `rpc.mjs:createPackageDeliveryRpc({env,fetchImpl})` maps only fixed service-role delivery RPC names. `supabase/config.toml` adds this function with `verify_jwt=false` because these explicit reader/publisher verifiers own authentication; default-off/auth failures must occur before Storage. Existing master snapshot/Archive code consumes the shared publication contract, not a second write path.

`createPackageDeliveryStorage({env,fetchImpl,now})` in `ppc-package/storage.mjs` implements `uploadObject(candidate,stream)`, `openObject(candidate)`, `signDownload(candidate)`, `removeObject(candidate)`. Use same-project Storage REST, exact bucket/derived key, bounded responses, no redirects/arbitrary URLs, no upsert and no upload capability returned to callers. Verify accepted method/stream/create-only semantics locally and at the deployment gate. `hash.mjs:createCiphertextVerifier()` uses incremental `node:crypto.createHash` for SHA-256 and optional legacy Git blob SHA-1, envelope/byte counters and backpressure. Parent verified local Deno 2.5.4 native hashing of 64 MiB in 64 KiB chunks (392 ms wall; RSS 57,548,800 bytes); this is not Supabase performance proof. No whole-package `arrayBuffer`, string/base64 conversion, JSON buffering or decrypting inside Edge.

Actions `createPackageDeliveryClient({endpoint,publisherSecret,fetchImpl})` in `scripts/package-delivery-client.mjs` implements `readCurrent()`, `reserve(metadata)`, `upload(reservation,bytes)`, `finalize(candidateId)`. Refactor existing publisher to use its current archive source and projected/encrypted output unchanged; SharePoint mode reads **current cache bytes**, validates digest/manifest/owner state, and replaces only Git write/deploy/ack with reserve/authenticated binary upload/finalize. Never fall back to the stale Git archive in SharePoint mode. Keep owner candidate input commits and existing full archive preservation. Queue reuse must also match requested `ownerImagesCommit`; another queued image job is reported pending/busy, never silently counted as this job's success. A queued ready candidate waits for cloud publication; it is not a successful publication.

MCP adds `get_queued_publication({})` and `confirm_sharepoint_publication({candidateId,generation,item:{driveId,folderId,itemId,versionId,fileName},readback:{download_url,file_id,mime_type?,file_name?}})` with strict schemas and actual `readback` fileParams. Retrieval returns `{candidate:null}` or `{candidate:{candidateId,generation,storageRevision,sha256,bytes,expiresAt,fileName,provider,driveId,folderId},downloadUrl}` for the sole ready candidate; no private Storage key or plaintext. Hosted code must download this to a real sandbox file before connector upload; a URL is never a file handle. Upload only the fixed candidate filename with create/no-overwrite semantics; after an uncertain result, fetch that exact path/item and compare bytes before retrying. Connector create/version behavior must be verified; otherwise hold rather than overwrite.

Readback download accepts only the existing exact trusted OpenAI raw-file origin/path policy, with a separate 64 MiB streaming cap and 120-second deadline; it never forwards OAuth/publisher credentials. Confirm actual bytes against the candidate before CAS. The authenticated worker supplies SharePoint provenance: a signed OpenAI URL proves byte transport, **not cryptographic SharePoint provenance**. Do not claim otherwise. Expired URLs require an authorized new raw fetch, not an expanded host allowlist.

ASCM Archive requires native immutable import receipt AND `qualifiesSharePointPublication(...)` from the same master/destination policy, with published revision >= accepted revision. Missing provider/receipt/digest, legacy GitHub acknowledgement, pending candidate, auth failures or readback mismatch return `archiveAllowed:false`. This requirement applies in seeding/sharepoint phases; legacy behavior remains for the default-off old path until cutover, and the new supervisor stays disabled meanwhile.

Reader streams only the current object whose immutable SharePoint receipt still matches, with octet-stream, `Content-Length`, `X-PPC-Package-SHA256`, `X-PPC-Package-Generation`, `X-PPC-Package-Candidate-Id`, `X-PPC-Package-Revision`, `Cache-Control:no-store`, no redirect and request-abort/backpressure propagation; expose those identity headers to allowed CORS origins. Existing package-client relay contract remains `{key}` -> binary. `downloadLatest({...options,onIdentity?}) -> Uint8Array` verifies actual SHA-256/length before invoking `onIdentity({provider:'sharepoint',generation,candidateId,sha256,bytes,storageRevision})`; the approved `/functions/v1/ppc-package/api/package/latest` service path requires these identity headers and fails closed if missing/malformed, while generic legacy relays retain their existing behavior. `package-ui` passes this value as `deliveryIdentity` to `importProjectPackage(file,{...options,deliveryIdentity})`; app compares any checked snapshot and records `loadedPackageInfo:{version:2,...deliveryIdentity,loadedAt}`, retaining version-1 blob identity for legacy imports. Preserve busy/pending-draft guards, complete images, access-key lifetime and native navigation. No new browser polling.

## Migration, costs and release gates

New code defaults off and coexists with legacy publisher/config. In an explicitly approved bounded cutover, freeze old Git publication, enter `seeding`, and use explicit `--seed-delivery-cache` pinned to `https://monocraft.github.io/PPC/data/master_ppc.pkg` and the verified hash/size above; no arbitrary source URL. Actions validates/decrypts with its existing secret and requires the seed's native published revision and actual Git blob identity to equal the **existing trusted GitHub publication record**, plus original sourceSha/marker integrity. The seed may lag the current accepted database revision: it initializes only archive input/current ciphertext at that already-published revision, never bootstraps/overwrites accepted facts. Seed uses `manifestSha256=null` and `ownerImagesCommit=null`; its pinned bytes/trusted blob/marker validation replaces the ordinary current-export digest check, so never compare its older manifest to current accepted facts. The worker confirms exact seeded SharePoint item/version by real raw readback. Seed requires no current receipt; older/unmatched metadata, altered marker, advanced public bytes or races hold for reviewed seed reconciliation, never infer a replacement identity.

After seed, the next ordinary producer projects the **current accepted export** over seeded archive bytes and publishes its own qualifying SharePoint receipt before any new-report Archive gate may pass. Even when projected content is unchanged, a seed current receipt forces an ordinary publication at the next generation; an unchanged-content shortcut must not leave the supervisor permanently behind the seed-only Archive gate. Seeding alone never permits new report Archive or declares the latest accepted package current; if accepted facts are ahead, public status remains pending until catch-up. No automatic Git fallback.

After seed verification, atomically select `sharepoint` policy, select producer transport `PPC_PACKAGE_PUBLICATION_MODE=sharepoint`, and publish service package endpoint configuration. Leave tracked historical packages and Git history intact; service-mode Pages artifacts need not include a stale package. Retain old pipeline code for rollback, but do not reactivate Git publication/Archive gates automatically if delivery fails. Switching back is a separately reviewed configuration/data-consistency action.

Cost/access calls: retained ciphertext is a real encrypted mirror (approved); one candidate adds bounded temporary storage. Verification, producer reads, cloud downloads/readbacks and each browser open add transfer/Edge/Storage requests; no unverified dollar estimate. Existing publisher secret gains only fixed-package staging/current-read authority; existing owner OAuth gains fixed-folder publication acknowledgement; reader-key authority gains only current ciphertext delivery. No additional Microsoft access or broad credentials.

Local implementation uses synthetic fixtures, required PGlite and outbound-blocked signed OAuth/storage/MCP integration. Supabase's documented limits are 256 MB memory, 2 seconds CPU and 150 seconds request idle timeout (paid worker lifetime 400 seconds); the Storage global file limit overrides bucket limits and its current setting is unverified. [Edge limits](https://supabase.com/docs/guides/functions/limits), [Storage limits](https://supabase.com/docs/guides/storage/uploads/file-limits), [two-hour signed upload capability](https://supabase.com/docs/reference/javascript/file-buckets-createsigneduploadurl). Verify global limit >=64 MiB during approved deployment; changing it is a separate disclosed configuration action, not a source assumption.

Release additionally requires explicit action-time security approval for managed OAuth/client/hook/Storage policy/secret/configuration changes, reviewed default-off deployment, actual initial+refresh OAuth interoperability, package-scale cloud upload/readback and measured Edge binary-upload CPU/memory/timeout behavior, then one chosen real monthly report through immutable receipt -> qualifying SharePoint publication -> exact-message Archive. A runtime/size-limit failure holds activation for a reviewed transport change; do not silently allocate a new paid service. Only after that gate may the separately authorized quiet PC-off schedule be enabled. The existing seed or a passing local test is not completion.
